# 文档规范

状态：Current。目标是让下一个 Agent 不靠聊天记录也能接手。

## 一事实一页

- 每个行为只有一个“拥有者”页面；其他页面链接过去，不复制。
- 改行为时，同一个改动里更新拥有者页面；纯重构不改契约可以不写。
- 页面里的事实必须能指到源码文件/符号；不要抄会快速过期的实现细节。

## 状态标注

每个现行页面第一行写：

```text
状态：Current。最后核对：YYYY-MM-DD，对应 <commit>。
```

- **Current**：当前代码行为。
- **Unverified**：实现了但没实机/真实账号证据；必须写明缺什么。
- **Historical**：`docs/history/` 下的旧计划/调研/报告，可以过时。
- **Proposed**：提案放 issue 或 `projects/`，不混进 Current。

## 新页模板

```markdown
# 标题

状态：Current。最后核对：...

## 职责与边界
## 源码入口
## 运行时路径
## 状态/数据
## 约束
## 验证
## 未验证项
## 相关
```

## catalog 与链接

- 新增/删除页面时同步 `docs/catalog.json`（id 唯一、path 存在、summary 一句话）。
- 运行 `npm run docs:check`：检查 catalog 路径、页面互链、禁止的旧路径。
- 相对链接以当前文件为基准；不要写机器绝对路径。
- 历史文档可以保留旧路径描述，但要在页首标明 Historical。

## 历史归档

- 计划、调研、一次性报告放 `docs/history/`；不要删，它们是决策证据。
- 旧文档如果仍描述现状，先迁移/重写再归档，避免两份真相。

## 写作

- 中文为主；代码标识、命令、API 名保留英文。
- 短句、具体；写“怎么做 → 得到什么”，不写口号。
- 不写“未来会”“下一步计划”进 Current 页面；提案放对应位置。
- 不把过程笔记、生成说明、TODO 写进面向读者的页面。
