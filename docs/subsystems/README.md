## 改动前

1. 找到拥有该行为的页面，读“约束”和“验证”。
2. 顺着源码链接确认实现，不要只看本文。
3. 改完同步更新本页表格里对应页面的“当前行为”；如果新增子系统，在 `docs/catalog.json` 加条目。

## 页面模板

新页至少包含：状态、职责与边界、源码入口、运行时路径、状态/数据、约束、验证命令、未验证项。

## 维护一份 reference

改变一个已文档化的职责、接口、状态迁移、运行时路径、兼容规则或失败行为时，在同一个改动里更新拥有该事实的页面。纯内部重构、不改变这些契约的，不需要改文字。

- 每个事实只放在一个页面；其他页面链接过去。
- 链接源码文件与命名符号，不复制会快速过期的实现细节。
- 说明字段含义与约束，而不只是签名。
- 新页面至少写：职责与边界、真源、主运行时路径、状态迁移、约束、验证命令、失败/兼容行为。
- 当前行为与提案分开；提案放 issue 或 `projects/`，不要混进 Current 页面。

## 描述一个改动的语义变化

对受影响的每个子系统，说明：触发条件、改前行为、改后行为、接口/状态/兼容性/失败行为的变化。链接对应 reference、实现和验证证据。纯重构要明确说“契约不变”。

这是作者给审查者的说明，审查者仍需对照 diff 与代码验证；文档更新本身不证明实现。

## 审查一个改动

1. 找到受影响的子系统和真实运行时路径。
2. 对照 base/head 代码，追踪调用方与状态迁移，不只看出改动的行。
3. 检查契约变化是否写进拥有者页面，源码链接是否有效。
4. 检查引用的测试/运行证据是否真的覆盖了声称的行为；没跑的检查要列出来。
